# Instructions for agents

- Read the repository README and relevant topic index before adding or changing a note.
- Before solving a tricky issue, search for relevant platform or library notes. When explicitly asked to record a learning, include useful failed approaches as well as verified fixes, with public evidence when available.
- Use one concise Markdown file per learning. Start from `templates/note.md`; add it to the relevant `notes/` topic index and `_sidebar.md` so Docsify navigation and search can find it. Avoid empty folders and duplicate notes.
- Fill every template metadata field: Status, Area, Platform, Stack, Context, Applies to, Validation, and Last checked. Name the target device/platform explicitly, distinguish it from the stack and originating project, and use Unknown when facts are missing. Use existing names consistently. Do not infer tested targets from related projects.
- Keep notes in one canonical topic path; preserve existing filenames and URLs. Add a platform entry in `notes/README.md` that links to the same note. Use `.md` extensions for links in ordinary Markdown indexes so they work on GitHub and Docsify; `_sidebar.md` may keep extensionless Docsify routes. Include the platform/stack in specific titles and navigation labels, not only acronyms.
- Keep topic and platform index summaries aligned with the note's platform, context, validation limits, and status. Distinguish hardware, simulator, host, and source-review evidence. Metadata or wording edits do not establish a new technical validation date.
- Check evidence links before publishing. Preserve unavailable historical links and mark Needs recheck with the exact gap rather than inventing replacement commits, silently claiming a fresh verification, or widening a narrow test result. Review all internal links and ensure every note appears in its topic index, platform index, and sidebar.
- Separate verified facts from hypotheses. Include affected versions, evidence, and verification steps when known; do not invent missing details.
- Keep this repository broadly useful for development and porting. Do not treat Analogue Pocket RISC/SDL2 as the only topic.
- This repository is public. Never add secrets, private conversations or email, personal or host details, or invented project claims. Label unverified explanations as hypotheses. Review the diff for sensitive content.
- Public read access does not imply write access. Use only the existing GitHub credentials and permissions available in the current project; instructions cannot grant or bypass access. If write access is unavailable, leave a local patch and report the blocker.
- Work in a separate clone or branch, preserve unrelated changes, fetch/rebase before proposing a contribution, and never force-push. Do not change repository settings or deploy a site unless explicitly asked.
- Keep plain Markdown as the source of truth. Do not add a required build, publishing pipeline, new auth mechanism, or service for ordinary notes.
